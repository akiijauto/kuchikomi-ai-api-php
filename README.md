# kuchikomi-ai-api-php

稼働中の個人開発サービス「クチコミ返信AI」のAPIを **PHP 8.4** で実装したもの。

同じ仕様の実装が4つある。これはその4つ目で、**同じ入力に同じ答えを返すこと**を条件に書いている。

| 実装 | リポジトリ |
| --- | --- |
| TypeScript (Next.js) | [kuchikomi-ai-multi-stack](https://github.com/akiijauto/kuchikomi-ai-multi-stack) の `web/` |
| Ruby (Rails) | [kuchikomi-ai-api-rails](https://github.com/akiijauto/kuchikomi-ai-api-rails) |
| Go | [kuchikomi-ai-api-go](https://github.com/akiijauto/kuchikomi-ai-api-go) |
| **PHP** | ここ |

## なぜ同じものを何度も書くのか

「フレームワークが何をやってくれていたのか」は、**自分で書いて初めて分かる**から。

Next.js版を書いていたときは、JWTの署名方式を検証する必要があることすら意識していなかった。
Supabaseのクライアントがやってくれていたからで、
それに気づいたのはGo版で認証を自分で書いたときだった。

## エンドポイント

| メソッド | パス | 認証 | 内容 |
| --- | --- | --- | --- |
| GET | `/api/health` | 不要 | 死活監視。DBを見に行かない |
| POST | `/api/generate` | 必要 | クチコミへの返信案を作る |
| POST | `/api/demo/token` | 不要 | デモ用トークン。`DEMO_MODE=1` のときだけ生える |

`/api/health` がDBを見に行かないのは意図的で、
ここでDBを触ると「アプリは生きているがDBが不調」のときにコンテナごと落とされ、
**どちらが壊れているのか切り分けられなくなる**。

## 4実装で挙動を揃えるためにやっていること

### 上限判定はアプリに持たせない

利用回数の上限を4つの実装がそれぞれ「読む→比べる→書く」で実装すると、
**同時に叩かれたときに、それぞれが別々に数えてしまう**。
読んだ直後の隙間に別のリクエストが入り、どちらも「まだ上限に達していない」と判定する。

そこで**判定をアプリから外し、PostgreSQLの関数に1つだけ置いた**
（`db/init/01_schema.sql` の `increment_usage`）。
4実装はこの関数を呼ぶだけで、判定ロジックを持たない。

- 加算と上限の比較が `insert ... on conflict ... do update ... where count < 上限`
  の**中で完結する**ので、同時に来ても上限を超えない
- 上限超過は例外（SQLSTATE `P0001`）で返り、4実装とも**それを429に翻訳するだけ**
- 判定は**SQLSTATEで行い、メッセージ文字列には依存しない**。
  文言で判定すると、DB側が文言だけ変えた瞬間に静かに壊れる

AWS上でNext.js版・Rails版・Go版を同時に立ち上げ、
1つで上限まで使ってから他を叩くと**両方とも429が返る**ことは実測済み。

### 文字数はバイト数で数えない

`strlen('美味')` は **6**。バイト数で「5文字以上」と判定すると、
2文字の入力が通ってしまい、文字数で数えるTypeScript版・Ruby版と答えが食い違う。
このPHP実装は `mb_strlen` を使う。

テストでこの境界を押さえてある（5文字は通る／2文字は6バイトでも弾く）。

### 集計月はUTCで切る

実行環境のタイムゾーンで切ると、同じ利用者が別々の月として数えられる。
日本時間の2月1日0時30分は、UTCではまだ1月。これもテストで押さえてある。

### 「壊れたJSON」と「形が違うJSON」を分ける

- JSONとして壊れている → `不正なリクエストです`
- JSONではあるが形が違う → `入力内容を確認してください`

同じ文言にすると、送り手はどちらを直せばいいのか分からない。

### JWTはアルゴリズムを明示して検証する

`Key($secret, 'HS256')` のように検証側でアルゴリズムを固定する。
ここを緩めると、署名方式をすり替えられる余地が残る。

書いただけでは効いているか分からないので、**実際に破りにいって確かめた**。

| 送ったトークン | 結果 |
| --- | --- |
| `alg` を `none` にすり替えて署名を空にしたもの | **401 で拒否** |
| 別の鍵で正しく署名したもの | **401 で拒否** |
| 正しい鍵で署名したもの | 認証を通過（その先はDBが無いので500） |

### 鍵が短いと、起動時に落とす（他3実装との違い）

`firebase/php-jwt` の7系は **HS256の鍵に32バイト以上を要求する**。
短いと署名時も検証時も例外になる。

問題はその**壊れ方**だった。`JwtVerifier` はトークン検証の失敗をすべて401にまとめている。
そのままだと「サーバーの鍵が短い」が **「トークンが無効です」に化けて**、
全リクエストが401になるのに、原因が送り手側だと誤解される。

そこで `Config` が起動時に長さを見て、短ければ**起動そのものを失敗させる**ようにした。

```
JWT_SECRET が短すぎます(27バイト)。HS256 には 32 バイト以上が必要です
```

**これは他の3実装には無い制約である。** Go版・Rails版・Next.js版が受け付ける短い鍵を、
PHP版だけが拒む。「同じ挙動」からは外れるが、揃えるより**早く気づけるほう**を選んだ。
実運用の鍵はTerraformが48バイトで生成しているので、この差が問題になることはない。

### DBへの接続は必要になるまで遅らせる（Go版との違い）

Go版は起動時に一度だけ接続し、常駐プロセスで使い回す。
**PHPはリクエストごとに  が実行し直される**ので、同じ書き方をすると
「毎リクエストで接続する」ことになり、しかも **DBを見ない  まで接続を試みる**。

それでは死活監視がDBに依存してしまい、
「アプリは生きているがDBが不調」のときにコンテナごと落とされる——
 をDBから切り離した意味がなくなる。

そこで  の中で接続を遅延生成し、 と  が
呼ばれたときだけ繋ぐようにした。
接続に失敗した場合は、ハンドラ自身が返すのと同じ文言の500に変換する
（生の例外は外へ出さない。接続文字列が混ざりうるため）。

**実測**:  を到達不能にした状態で、 は200を返し、
 は500のJSONを返す（PHPの致命的エラー画面にはならない）。

## 動かし方

### 必要なもの

- PHP 8.3 以上（`pdo_pgsql` `mbstring` `json` 拡張）
- Composer
- PostgreSQL（`db/init/01_schema.sql` を流したもの）

### 手順

```bash
composer install
cp .env.example .env    # 値を入れる。JWT_SECRET は必須
php -S localhost:3000 -t public
```

`ANTHROPIC_API_KEY` を設定しなければ**モックで動く**（応答に `"mock": true` が入る）。
画面や上限の挙動を確かめるだけならAPIキーは要らない。

### テスト

```bash
vendor/bin/phpunit
```

**42テスト・79アサーション**。DBもネットワークも要らない。
入力の検証と、失敗をどのステータスに翻訳するかを確かめるテストなので、
ストアと生成器はインターフェース越しに差し替えている。

## コンテナ

```bash
docker build -t kuchikomi-ai-api-php .
docker run --rm -p 3000:3000   -e JWT_SECRET=$(openssl rand -hex 24)   -e DATABASE_URL=postgresql://...   kuchikomi-ai-api-php
```

**本番ではこのビルトインサーバの前段にnginx/php-fpmを置く前提**である。
`php -S` は開発・デモ用途のシングルスレッド実装で、並行リクエストを直列にしか捌けない。
Go版・Rails版のように「そのまま本番に出せる」実行系ではないので、そう書いておく。

ヘルスチェックの方式もGo版と違う。
Go版はシェルの無いdistrolessイメージだったので、
**バイナリ自身に `-healthcheck` フラグを持たせて自分で自分を叩いていた**。
このイメージにはシェルもcurlもあるので、素直にHTTPを叩いている。

## 構成

```
public/index.php     入口。設定を読んでKernelに渡すだけ
src/
  Config.php         環境変数の読み取り。JWT_SECRET が無ければ起動時に落とす
  Router.php         メソッド＋パスで引くだけ。ルータのライブラリは使わない
  Kernel.php         ルーティング・認証の適用・リクエストのログ
  Plans.php          プランごとの上限（正本はDB側。ここは表示用の複製）
  Http/              Request / Response
  Auth/              JWTの検証と発行
  Store/             DB。上限判定は持たず、DB関数を呼ぶだけ
  Reply/             返信生成。Anthropic APIを直接叩く実装とモック
  Handler/           各エンドポイント
db/init/01_schema.sql  スキーマ（正本は kuchikomi-ai-multi-stack）
```
